## 3. 首版范围与不做事项

### 3.1 P0：首版必须完成

1. 顶部双入口：AI App、LLM 模型；首次打开默认 AI App，之后恢复上次使用的榜。
2. 两榜各自独立保存档位、同行顺序、待排名顺序、自定义标题及当前筛选。
3. 全部条目初始待排名，不内置强弱结论；稳定的初始展示顺序只表达编目顺序。
4. 搜索名称与别名；筛选开发者/品牌、来源（全部/内置/自定义）；数据提供分类时再提供分类筛选。
5. 一份主排名投影成多个筛选视图；筛选切换不新建排名，不丢失隐藏条目。
6. 鼠标、触屏拖动，同行插入；点按选中后选择档位、前移、后移、移回待排名。
7. 用户添加、编辑和删除自定义条目，内置与自定义条目混合排序。
8. 自动本地保存、写入失败提示、损坏存档保护、撤销、仅清空当前筛选下已排名的卡片。
9. 结果图预览与分页：导出当前应用筛选下的所有条目，包含待排名，不受 DOM 分批数量限制。
10. Toy 浏览器保存；小红书保存相册及分享到笔记编辑器，缺少宿主时提供正确降级。
11. 新项目身份、数据和资源白名单、双端检查、ZIP 清单与可复现验收记录。

### 3.2 P1：首版交付后再评估

多套个人榜、按用途分别保存榜、用户上传自定义图标、存档导入导出、更多主题、自定义档位名称、用户收藏名单、同模型多服务商体验细分。不要为这些功能提前引入账户、服务端或复杂配置界面。

## 4. 信息架构与交互

### 4.1 页面布局

```text
产品名 AI 从夯到拉                       简短使用说明
[ AI App ] [ LLM 模型 ]
榜单标题（可编辑）
搜索名称/别名    品牌筛选    来源筛选    可选分类
范围摘要：当前 N 项，已排 M 项   [清除筛选] [添加条目]
夯       卡片 → 卡片 → …
顶级     …
人上人   …
NPC      …
拉       …
待排名   分批显示，按需展开
保存状态
[撤销] [清空场上]                       [生成结果图]
```

初始标题为「AI App 从夯到拉」「LLM 模型从夯到拉」，可编辑到 30 个 Unicode 码点。主界面突出条目身份和排名操作，核验链接、模型 ID 等长信息放详情内，避免把维护字段堆在卡片上。

卡片显示图标、名称；LLM 可显示名单提供的版本/规格短副标题。自定义条目有小标签。卡片名称最多显示两行，详情保留全文，不能只靠相同品牌图标区分模型。所有操作按钮目标尺寸至少 44×44 CSS px。

### 4.2 搜索与筛选

- 搜索、品牌、分类、来源只影响可见集合；维度之间取交集，分类多值内部取并集。
- 首版默认输入/选择后直接应用，搜索防抖约 150 ms；回车/输入法完成组合时立即应用，不能在中文输入组合中反复重绘。
- 搜索内容保留原输入；匹配副本做去首尾空白、大小写与常见全角字符规范化。不使用用户输入构造正则表达式。
- 分类是可选元数据；无分类条目归入「未分类」，默认全部时始终可见。不得根据模型名臆测能力。
- 「清除筛选」清空搜索并恢复所有筛选为全部，不改变排名；「清空场上」改变当前视图的已排名条目，两者明确区分。
- 拖动时冻结当前可见集合，搜索/切换榜/开弹窗先取消拖动。只按最终已应用的筛选执行清空与导出。
- 无结果时显示清除筛选入口，不能将完整榜误判为空。

### 4.3 拖动、点按与清空

拖动从卡片任意位置开始；识别少量移动阈值区分点击，保证纵向滚动可用。边缘拖动自动滚动；第二根手指、Esc、失去指针捕获、窗口隐藏时取消拖动，恢复原位置。不能用全局时间窗拦截其他控件的有效点击。

同榜内同档按数组保存真实同行顺序。筛选内重排用可见槽位合并：例如完整行 `[A, X, B, Y]`，只显示 A、B，交换后为 `[B, X, A, Y]`；X、Y 的档位和相互顺序保留。跨档后目标行无可见槽位则追加到该档末尾。

「清空场上」仅把当前应用筛选内已定档卡片移回待排名，保持原待排名区顺序，按档位从高到低、同行从左到右追加清出的条目。0 张禁用，1～2 张直接执行，3 张及以上弹窗确认，并显示实际张数；不按屏幕上已渲染张数计数。整个操作是一步撤销，不影响标题、隐藏条目和另一个榜。

### 4.4 视觉方案

采用清爽的科技工具风格：中性深色或浅色底、高对比文本、红到蓝的五档色带，卡片和结果图保持一致。首版只实现一套主题；不用红警军徽、阵营标识、军绿指挥界面文案。动效服务于拖动和状态反馈，不加入无关 3D、粒子、背景视频或音效。尊重减少动态效果的系统偏好。

## 5. 名单接入协议：与另一个会话协作

### 5.1 分工与接入原则

另一个会话负责条目收录、模型粒度、真实名称与分类、官方资料和图标来源。本会话后续负责程序和数据校验。框架开发不等名单定稿；先用明确标记为测试数据的虚构 App/模型覆盖各种边界，测试数据不进入正式包。

拟定输入文件为 `data/ai-apps.json`、`data/llm-models.json`、`assets/ai-icons/manifest.json`。实际文件名若由名单会话另定，先通过适配脚本转换成下述内部格式，不要求对方重做名单。首次读取时记录文件哈希，避免覆盖对方未完成工作。

每项至少需要稳定唯一 ID、所属榜、显示名称；其他元数据缺省时允许框架运行。正式内置名单需完成来源核对，无法核实的条目标记为候选，不假装已核验后发行。

```json
{
  "catalogRevision": "example-not-for-release",
  "verifiedAt": null,
  "items": [
    {
      "id": "builtin:app:example-assistant",
      "kind": "app",
      "name": "示例助手（测试数据）",
      "aliases": ["Example Assistant"],
      "providerId": null,
      "categoryIds": [],
      "subtitle": "",
      "familyId": null,
      "modelIdentity": null,
      "iconKey": null,
      "lifecycle": "unknown",
      "sources": [],
      "verifiedAt": null
    }
  ]
}
```

`kind` 只能为 `app` 或 `llm`；ID 是不可变内部标识，不用可变名称或数组下标当 ID。`providerId`、`familyId`、分类需要引用独立字典；`modelIdentity` 作为可选结构预留官方模型 ID、版本/快照、是否别名等信息，不能反过来决定 UI 必须按某粒度收录。

### 5.2 身份与版本规则

- App 和模型是不同实体；App 使用哪些模型不构成同步排名关系，不能从 App 排名自动生成模型排名。
- 模型粒度服从最终名单。无论选择系列还是具体版本，条目内部 ID 都必须稳定；新版本是否新建条目由编目决策明确记录。
- 改名只更新 `name/aliases`，保留 ID；新身份使用新 ID，默认进入待排名，不能沿用旧条目排名制造“自动升级”。
- 官方模型 ID、日期快照、滚动别名的含义因供应商而异。不要把所有无日期 ID 一概视为浮动别名；核对对应官方文档后记录。
- 多个平台提供同一模型时，不因 URL 不同自动重复建条目；是否区分部署服务由名单粒度决定。
- 不写“最新/最强”这类无法长期稳定的身份文案。不维护未经核验的价格、上下文窗口、开源许可等字段。

### 5.3 下架、移除与名单更新

`lifecycle` 可为 `active/preview/deprecated/retired/unknown`，只在有资料时填写，默认 `unknown`。条目下架不等于从数据库删除；已知历史条目可以继续供用户表达体验。

名单升级必须按 ID 协调存档：新增 ID 追加待排名；已有 ID 的档位与顺序不变；名称/图标更新不改排序。真正移出目录的 ID 转入存档的 `unavailablePlacements`，保留条目快照、原档位及相邻锚点/原下标，不立即丢弃。相同 ID 恢复时，在原档位按仍存在的锚点恢复，否则使用限幅原下标，不能重复插入。此归档不显示在普通榜，也不进入结果图，可在更新提示里说明数量。

### 5.4 图标规范

品牌共用图标文件，通过 `iconKey` 引用；同一模型系列多个条目可共用同一文件，身份由名称/副标题区分。优先使用有明确来源的官方素材；保存来源 URL、取得日期、使用说明及 SHA-256。无法确认可用素材时，采用自行绘制的首字母/中文短字色块，不借用其他产品图标。

图标只使用包内相对路径，不使用在线 favicon 服务。推荐 96～192 px 的 PNG/WebP，优先输出兼容 Canvas 的本地栅格图；构建期按字节哈希去重。页面与海报共用同一回退函数；加载失败显示确定性的色块和文字，不让一张图标中断整张海报。色块颜色由稳定 ID 派生，不能用名字变化导致同卡颜色跳变。

## 6. 用户自定义条目

### 6.1 首版交互与限制

在当前榜点击「添加条目」：弹窗内榜单类型固定为当前榜；必填名称，选填开发者/品牌文字、一个已有分类和简短副标题。模型的版本可写入副标题，不强制 API 模型 ID。保存后追加到当前榜待排名末尾，提示添加成功。

建议产品限额：每榜最多 50 个自定义条目，总计 100 个；名称 1～40 个 Unicode 码点，品牌 0～30，副标题 0～40。限额为首版可调整预算，不是平台限制。达到限额时保留已输入内容并给出说明，不静默截断。名称去首尾空白后不得为空；字段以纯文本渲染，不解析 HTML。

首版自定义图标使用名称短字＋稳定 ID 色块，不要求选图，不接收任意 URL，不增加图片上传、裁剪与大图存储。用户自选图片放入 P1，以免首版的离线持久化与分享链路被图片容量拖累。

### 6.2 编辑、删除与重复

- 自定义 ID 使用 `custom:app:...` 或 `custom:llm:...` 独立命名空间，在当前存档内检测碰撞。不能假定所有容器都支持 `crypto.randomUUID`；实现应有局部兼容方案。
- 编辑保留 ID、档位、同行位置，不允许直接更改所属榜。若改名后不再满足当前搜索/筛选，提示其已保存但当前不可见。
- 添加后若不匹配当前筛选，提示并提供「查看该条目」操作，先在原榜清除必要筛选再定位，不因看不见让用户重复添加。
- 名称规范化后与同榜现有条目重名，先提示并允许用户返回修改或确认仍添加；不自动与内置条目合并。品牌相同不代表实体相同。
- 只能编辑/删除自定义条目；内置条目提供详情，不提供伪编辑入口。自定义条目没有“官方已核验”标签。
- 删除前始终确认，说明只删除本地自定义条目；删除后移除其任何排名引用，恢复可通过撤销完成。不能误删内置 ID。
- 新增、编辑、删除均为可撤销事务；恢复删除时同时恢复条目元数据和原排名。先做容量检查，再变更，避免只写条目或只写位置。

### 6.3 筛选字典与条目详情

自定义品牌以独立键表示，不覆盖内置品牌记录；筛选选项来源于当前有效目录与自定义条目合并结果。无品牌条目进入「未填写」。自定义与内置来源可筛选，但共享当前榜主排名。详情显示名称、品牌、可选副标题、来源；内置条目可显示核验日期，自定义显示「用户添加」。

## 7. 状态、存档与撤销

### 7.1 状态结构

```text
applicationId: ai-tier-list
schemaVersion: 1
catalogRevision: <编目版本>
activeBoard: app | llm
boards:
  app: { title, tiers, unranked, unavailablePlacements }
  llm: { title, tiers, unranked, unavailablePlacements }
filters:
  app: { search, provider, category, source }
  llm: { search, provider, category, source }
customItems: { <customID>: 元数据 }
savedAt: ISO时间
```

持久化只保存完整主榜，不保存筛选投影的独立副本。任一有效条目在所属榜的五档＋待排名中恰好出现一次，两榜不能相互引用对方 ID。归档项单独验证。对象映射使用安全键检查/无原型对象，导入的 ID 不得触发 `__proto__` 等原型属性问题。

### 7.2 存储隔离与可靠性

Toy 使用 `ai-tier-list:toy:save:v1`，小红书使用 `ai-tier-list:xhs:save:v1`。另设对应备份键。严禁读取、迁移或写入 `ra2-tier-list:*`；新应用与旧应用并不是一次存档升级。

排名和自定义条目放同一有版本号的存档信封，避免跨键半完成。操作后约 300 ms 防抖保存；页面隐藏时尽力同步落盘，不只依赖离开页面事件。保存状态区分「待保存/已保存到本机/保存失败」；配额不足或被禁用时允许本次会话继续排名，并明确刷新可能丢失，不显示假成功。

读取时验证应用 ID、版本、结构、字段长度、总条目数、唯一性和引用。未知新版本存档或损坏内容不原地重置，不用初始状态覆盖；保留原字节，进入只读保护/临时会话，并提供用户明确选择恢复备份或重新开始的入口。备份只用通过验证的最近成功存档，不能拿损坏值覆盖好备份。

这些是本机草稿；不同平台、浏览器、设备不自动互通，系统清理也可能导致丢失。首版不承诺永久保存或跨设备同步。

### 7.3 撤销

每榜保留最近 20 次业务事务，仅当前会话有效。支持移动、同行重排、清空场上、自定义新增/编辑/删除、标题提交。切换筛选不计一步；不能在逐字符输入标题时塞满历史。撤销操作同时恢复有关元数据和排名，并重新应用当前筛选。

为了避免全局目录回滚影响另一个榜，每榜历史快照仅包含本榜主排名及本榜自定义条目；跨榜切换不改变历史。撤销不回滚内置名单版本，名单协调完成后重置旧会话历史并说明原因。所有变更先在内存生成并校验完整候选状态，校验成功再提交 UI 和保存队列。

## 8. 技术实现方案

### 8.1 技术取舍

保留现有无运行依赖的 HTML/CSS/JavaScript、Canvas 2D、Node 构建和 Python 打包。首版不为改主题重建 React/Vue 工程，不引入 tldraw 完整编辑器。只复用自由拖动、点击选择等交互思想，具体实现继续用已有 DOM 排名结构。

浏览器交付 JS 按 ES2017/Chrome 61 基线编写；Node 构建脚本可用当前环境支持的语法。兼容性以最终产物为准，现代 Web API 逐项做能力检测。不把现代桌面 Chrome 通过等同于旧 WebView 真机通过。

将 `window.RA2` 替换为项目专属 `window.AITier`（或局部模块导出后统一打包），不要保留一套 AI 逻辑、一套游戏逻辑双轨运行。域对象使用 `kind/app/llm`，取消 `lastGameVersion`、`ra2|units`、T4 继承等不相关分支。

### 8.3 构建和平台隔离

一套业务、两个平台适配器，以构建白名单生成 `dist/toy`、`dist/xhs`。首版两端条目范围与核心功能相同；只在宿主能力层分开，不能出现某端缺少自定义条目或排名规则不同的隐性分叉。

构建和打包入口分别支持指定平台，版本配置互相独立；只构建一个平台不得覆盖另一个平台的旧发行 ZIP。构建前验证目标绝对路径限定在新项目 `dist` 内。ZIP 中只含入口及运行资源，不包含旧游戏图标、原始抓取资料、测试数据、源映射、Git、文档或旧 ZIP。

## 9. 结果图与双端能力

### 9.1 导出契约

用户点击生成时，冻结榜单类型、标题、当前已应用筛选、完整可见排名、条目显示元数据和目录日期的快照；后续编辑不改变已生成图片。导出包含当前筛选所有卡片及待排名，顺序与界面一致。主界面允许批次渲染，导出不能只截取屏幕上现有 DOM。

海报包含标题、App/LLM 类型、简短筛选摘要、五档与待排名、页码、目录核验/更新日期（有值才显示）、用户生成日期及「个人体验排序」说明。不伪装成官方评级，不显示无来源的性能分数。多页重复必要标识，空档保留五档结构，长名称用实测字宽换行，不简单按字符数切。

推荐每页不超过 50 项，画布不超过 400 万像素；宽度默认 1080，可选 720。分页布局应以实际高度预算为准，50 项只是上限。逐页生成，默认缓存当前页与少量邻页，避免把所有 Canvas 长期驻留。分享额外页面按顺序串行补绘并释放画布；实际内存需设备实测。

### 9.2 Toy

所有图片本地引用，适配 `/toy/<新slug>/` 子路径，不能用根绝对资源地址。通过平台适配器保存当前图片，浏览器缺少下载能力时保留预览并提示系统保存方式。

上一项目的「我的 GitHub」入口是 Toy 专属规则，当前新产品暂不自动加入；如后续要求保留，另明确目标完整 URL，并确保不进入小红书包。新产品封面、标题、作品 ID 及 slug 全部单独确认，不复用旧审核指令。

### 9.3 小红书小工具

按已读取的 `minitool-zip-builder` 技能：纯本地、无运行时网络，资源全部随包；不使用外链、新窗口、浏览器下载、剪贴板、Worker、WASM 或动态代码执行。`index.html` 位于 ZIP 根，引用相对路径。用户自定义信息在页内表单完成，不用 `window.prompt`。

保存相册按技能文档使用完整 PNG data URI → `writeTempFile` → `saveImageToPhotosAlbum`。分享通过 `window.xhs.miniTool.postNote`，图片在 `mediaInfo.image_resources[].url`，标题最多 20、正文最多 1000、每次 1～18 张，页序正确。实施时重读技能 reference 核对参数，不直接照旧封装猜测。

如结果超过 18 页，阻止自动分享并提示缩小范围/分批保存，不能静默丢掉后续页。分享期间锁定重复提交与相关控件；准备阶段取消弹窗后不再调用宿主；用户取消、接口失败后恢复可重试状态。接口成功只提示进入笔记编辑流程，不宣称已公开发布。无宿主时展示保存/截图说明，不做无效调用。
